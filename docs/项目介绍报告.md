# 学习计划 Agent — 项目介绍报告

**方向**：HUB 工作室 AI 部门 · Agent 组（大二·进阶）
**作品类型**：最小 Agent（手写工具调用循环）
**运行形式**：命令行交互程序

---

## 1. 项目定位

一个能替用户完成真实任务的最小 Agent：用户说出学习目标和每天可投入的时长，Agent 自主决定是否调用工具，生成逐日学习计划，经过校验后落盘；用户也可以查看当前计划、查询历史任务，或者让它记住自己的长期偏好。

它不是聊天机器人：模型本身不"记住"任何计划，所有持久化都由工具完成，计划是否合格由代码判断，而不是由模型自我声称。

选择这个题目的原因：学习计划是每个人都有真实需求、且结果可以被客观检查的任务——天数、每天时长、字段完整性都能用代码验证，正好用来演示"Agent 循环 + 程序侧校验"的价值。

## 2. 对应考核要求

| 第二档主线要求 | 本项目实现 |
|---|---|
| 一个完整循环：读状态 → 决定是否调工具 → 执行 → 结果回传 → 继续思考 | `agent.py` 的 `ask_agent`，手写多轮循环 |
| 至少一个具有实际功能的工具 | 四个：`create_plan`、`view_plan`、`list_history`、`remember_preference` |
| 明确的终止条件 | 最大轮数 5、单工具最多 2 次、总调用最多 10 次 |
| 不直接依赖现成 Agent 框架 | 未使用 LangGraph / Dify 等，循环与工具调度均为自写 |
| 自选方向 B（记忆）：记住用户偏好与历史任务 | `memory.py` 持久化用户画像，偏好注入提示词、历史按需查询 |

## 4. 运行方式与可复现性

**环境**：Python 3.12.7；`openai 3.41.0`、`python-dotenv 1.2.3`；模型通过 OpenAI 兼容接口访问 `api.deepseek.com`。

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

在根目录创建 `.env`（必需），写入 `DEEPSEEK_API_KEY=...`。缺少该 key 时，程序在启动阶段就会提示配置缺失并退出；Agent 的所有功能都需要调用模型，没有离线模式（`python storage.py` 不调用模型，但同样要求 key）。然后：

```powershell
python agent.py       # 启动 Agent 交互
python planner.py      # 单独测试"生成 + 校验 + 重试"层
```

程序启动时会提示"按 Ctrl+C 退出"。`examples/study_plan.example.json` 随仓库提供，可复制为项目根目录下的 `study_plan.json`；查看计划同样需要模型与 `.env`。计划和画像固定写入项目目录，不受启动目录影响。

## 5. 核心设计

### 5.1 Agent 循环

`agent.py` 的循环只有四个动作，反复执行：

1. 把当前消息列表发给模型，附带四个工具的 schema
2. 如果模型没有返回 `tool_calls`，说明它已经能直接回答，打印并结束
3. 如果返回了工具调用，逐个执行：解析参数 → 参数校验 → 调用对应 Python 函数 → 把结果包装成 `role: "tool"` 的消息写回对话
4. 回到第 1 步，让模型根据工具结果继续判断


### 5.2 工具设计

| 工具 | 参数 | 作用 |
|---|---|---|
| `create_plan` | `goal`（学习目标）、`days`（天数）、`max_hours`（每天上限） | 生成计划 → 四层校验 → 写入 `study_plan.json` |
| `view_plan` | 无 | 读取当前保存的那一份计划（含每天具体任务） |
| `list_history` | 无 | 返回最近 5 条历史任务的索引：目标、天数、时长 |
| `remember_preference` | `key`（偏好名称）、`value`（偏好内容） | 写入 `user_profile.json`，跨会话生效 |

工具描述里写清了适用场景，并在提示词中专门说明 `view_plan` 与 `list_history` 的区别：一个是"现在是什么"，一个是"做过什么"。这一区分是自测中发现问题后补上的——早期版本用 `view_plan` 回答历史问题，结果只能答出当前这一份。

### 5.3 终止条件

三重限制的作用并不相同：

- 单次请求最多 5 轮工具循环
- 同一个工具在单次请求内最多执行 2 次（防止反复重试）
- 工具总调用次数最多 10 次

后两条只会拒绝当次调用，并把错误回传给模型，循环本身不会停止；只有 5 轮用尽才会结束循环。结束时不会静默退出：程序会追加一条系统消息，要求模型基于已有结果总结"完成了什么、没完成什么"，并明确禁止再调工具。这次总结会额外发起一次模型请求，因此单次请求实际最多 6 次模型调用。

### 5.4 失败处理与自愈

这是本项目投入最多的地方，分两层：

**外层（工具调用）**：参数类型不对、学习目标为空、未知工具名、执行抛异常，都会被捕获，并以字符串形式作为工具结果回传给模型，让它自行修正参数再试；同时受"单工具 2 次"限制，避免无限重试。工具真实失败时，执行摘要里会如实显示为失败，不会说成成功。

**内层（模型输出）**：`planner.py` 对生成结果做四层校验，任何一层不通过，都会把具体错误（例如"第 2 项缺少 hours 字段""计划共安排了 2 天，用户要求 3 天""第 3 天安排了 3 小时，每天最多允许 2 小时"）拼回对话，要求模型重新生成，最多 4 次。

四层校验分别是：

1. JSON 语法解析
2. 数据结构校验：必须是对象、`goal` 非空、`plan` 非空列表、每项含 `day/task/hours` 且类型正确，`hours` 必须是有限数字
3. 天数校验：`plan` 的条目数必须等于用户要求的天数
4. 时长校验：每天的 `hours` 不得超过用户给出的上限

类型判断里特意排除了 `bool`——Python 中 `True` 也是 `int`，不排除会把非法值放过去。天数与时长都作为工具的结构化参数传入，不依赖模型从自然语言里自行理解。

### 5.5 配置与工程

- 模型名、文件路径、API 客户端集中在 `config.py`，避免同一个值散落在多个文件
- 计划和画像使用基于项目目录的绝对路径，从其他目录启动也不会写错位置
- 密钥从环境变量读取，可用 `.env` 提供；同名环境变量优先于 `.env`。`.gitignore` 已排除 `.env` 与 `__pycache__`
- 按职责命名（planner / storage / agent），使依赖方向清晰

### 5.6 自选方向 B：跨会话记忆

记忆不是"把聊天记录存下来"，而是把下一轮需要用到的事实单独存下来，在请求发出前放回上下文。实现时先把三种数据分开：

| 数据 | 位置 | 职责 |
|---|---|---|
| 当前计划 | `study_plan.json` | **状态**：现在是什么 |
| 用户偏好 | `user_profile.json` → `preferences` | **记忆**：下次怎么做得更贴合用户 |
| 历史任务 | `user_profile.json` → `history` | **日志**：用户做过什么 |

- **读（偏好）**：每次提问前调用 `format_memory()`，把偏好拼成几行文本注入 system prompt；没有偏好时返回空字符串，不产生噪音。
- **读（历史）**：**不在提示词中展开**，只保留一句"有历史记录，需要时调用 list_history 工具"。历史内容仅在用户明确询问时由工具读取。
- **写**：模型判断用户在表达长期偏好，调用 `remember_preference`；每次 `create_plan` 成功，程序自动追加一条历史记录，只保留最近 5 条。偏好 key/value 会压缩换行与多余空白，并分别截断到 50/200 字符，避免通过记忆注入提示词或占用过多上下文。
- **容错**：文件不存在、内容损坏或结构不正确时返回空画像，主流程继续；记忆写入失败不会回滚已经成功的计划生成。
- **边界**：只保存偏好与任务摘要，不保存完整对话；同名偏好直接覆盖。

**为什么历史不直接注入提示词**：这是本项目最有价值的一次自测修正。早期版本把最近三次任务原文拼进 system prompt，结果模型在调用工具之前就已经"看到答案"，问"以前制定过哪些计划"时只调 `view_plan`，再把提示词里的历史顺带提一句——`list_history` 事实上被架空了。改为"只提示存在、内容靠工具取"之后，查询历史才真正走完一次工具调用。

为什么用文件而不是向量库：偏好是结构化的短文本，键值对足够；引入向量检索会增加依赖，也会让"为什么召回这条"难以解释。

## 6. 现场演示脚本（约 3 分钟）

1. **先演示查看**：输入"看看我现在的计划"，模型调用 `view_plan`，终端打印当前计划与工具执行摘要。
2. **演示记忆写入**：输入"以后我每天最多学 2 小时"，模型调用 `remember_preference`，打开 `user_profile.json` 展示写入结果。
3. **演示生成**：输入"帮我制定一个三天速成 C 语言的学习计划"（故意不说时长），展示模型从偏好中取到 2 小时，然后走生成、校验、保存流程。
4. **演示历史查询**：输入"我以前制定过哪些计划"，模型调用 `list_history`，展示返回的是历史索引，而不是当前计划。
5. **演示跨会话**：按 `Ctrl+C` 退出后重新启动，输入"我有什么偏好"，展示偏好依然存在，说明它不是进程内变量。
6. **演示失败路径**（可选）：把 `max_hours` 说成很小时观察校验拦截；或手动把 `study_plan.json` 改坏后，观察 `view_plan` 提示计划不可用而不是程序崩溃。

## 7. 实测样例

一次成功运行生成的结果（示例见 `examples/study_plan.example.json`）：

- 目标：三天速成 C 语言
- 第 1 天：搭建 C 语言编译环境，掌握程序基本结构、变量与常量、基本数据类型、运算符、printf/scanf 输入输出，完成简单计算和输入输出练习，1.5 小时
- 第 2 天：学习 if/switch 分支、for/while 循环、函数定义与调用、参数和返回值、一维数组，完成分支循环与数组小练习，1.5 小时
- 第 3 天：理解指针基础、字符串与数组的关系，了解结构体，编写并调试一个综合小程序，如简易计算器或成绩统计，1.5 小时

每天时长均未超过用户给定的上限，天数与要求一致，字段完整，已通过四层校验。

## 8. 已知限制

1. **天数校验只统计条目数**：能保证"条数正确"，但不检查 `day` 标签是否从"第1天"连续编号、是否重复。
2. **只保留一份计划**：`save_plan` 覆盖写入，没有版本或历史。
3. **历史只有索引**：`list_history` 不返回每天的具体任务，且最多保留 5 条。

## 9. 改进计划

1. 增加 `day` 标签的连续性与唯一性校验，而不只统计条目数
2. 为记忆增加查看与清除命令，并对偏好 key 做白名单约束，避免同义并存
